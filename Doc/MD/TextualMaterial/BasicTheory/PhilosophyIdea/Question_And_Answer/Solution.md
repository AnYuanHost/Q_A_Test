# 解决方案

***

因为在前文中，已经随着探讨的深入重新区分了解决方案的概念，所以这里为其工程化定义进行阐述。作为第二种，解决方案应该指明如何将原本的父问题分解为更容易解答的子问题。更一般化的，问题将会按照先后关系，并发关系组成一个标准的流图的形式，那么解决方案就是维护这个流图如何进行改变的工具。如果父问题分解，便是将问答流图的子图，替换为一组新的子图，那么解决方案就负责为这个工作提供基本的信息。

***

## 1. 问答流图

在庞杂系统内核中，所有等待解答和已经解答完成的实际问题，都会通过问答流图管理来完成分解、操作和分析。这些问题将会按照其状态进行以下区分：执行状态，和是否可直接执行。

所有的问题都通过其前置问题的状态决定其执行状态。当一个问题作为原子问题执行了解答方法后，那么这个问题的状态就会变为执行完成，这也是问答流图的起点。如果一个问题，所有前置问题都已执行完成，而自身未执行，这种状态是等待状态。处于等待状态的节点将会被各种解决方案分析并操作，直到变成可以执行的原子问题。而可执行状态的问题则要求必须有一个映射与之一一对应，并通过其他模块走执行程序完成执行。

如果一个节点的前置问题中有等待状态或者可执行状态的问题，那么它就是不可执行状态的问题。必须等待前置的问题全部解决，才可以进入等待态或者可执行状态。而为了加速整个问答流图运行的速度，为不可执行状态的问题增加一个可直接执行前缀。凡是有这个前缀的问题，只要所有前置问题都已经执行完成，那么不进入可执行状态，而是直接进入等待状态。

一般情况下的状态转移：

<center>不可执行状态 -> 可执行状态 -> 等待状态 -> 执行状态 -> 执行完成状态</center>

## 2. 解决方案

在明确解决方案工作的目标后，只需要明确一个大问题：从通用的解决方案信息到具体的问答流图的子图替换的过程中，应该提供哪些信息，操作哪些信息？首先先明确通用的解决方案应该提供哪些信息。

解决方案本质上要完成子图替换，需要匹配原始的问答流图子图，并为待替换的问答流图的子图提供基本信息。首先就是结构信息，无论是匹配原始子图，还是生成子图，问题的结构都是固定的。固定的状态，固定的问题，固定的先后关系与并行关系。而固定的结构对应的是解决方案的本质特征，对应的是问题的本质特征，那么不固定的信息是什么也就清晰了。

回到问答体系中关于问题的定义，不固定的便是问题所发生的环境，或者说语境。这些额外的信息补充了问题，将它从理论拉入到现实。而解决方案将会在这个基础上，探讨如何维护语境相关的信息。好消息是，原始的问答流图中各个问题发生的语境一定是清晰的，坏消息是，那些子图替换时才新生成的语境难以被追踪。

也就是说，那些结构上的，或者可以通过已经存在的实体来确定的信息，只需要一个统一的方法便可以完成管理。但是，启发式才是问题足够开放的基础，才是庞杂系统的超越性所在。而这一部分如何启发，将会在问答流图和解决方案的具体实现模块部分进行阐述。
